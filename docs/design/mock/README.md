making design decisions before anything is built: put options side by side on
live screens, play their motion, hear their sounds, and let me pick.

## A new decision page

1. Copy `components.html` to a new file here and replace its `items` with a
   `ZK.decisions(mount, list)` call: each decision has a `key`, a `title`, a
   `why`, and `options`, each option a `name`, an optional `tag` (`today`,
   `suggested`), a `blurb` and a `draw()` that returns `ZK.screen(...)`.
2. Build one file from it, since an Artifact page carries everything inline:

   ```bash
   python3 tools/mockpage.py docs/design/mock/NEW.html /tmp/NEW.html
   ```

3. Publish `/tmp/NEW.html` as an Artifact with `capabilities: {db: {}}`. The
   picks land in its database, collection `picks`, one document per decision
   (`{choice, note, at}`), which the Artifact database tool reads back.
4. Write what was decided into DESIGN.md, and the values into
   `tools/designdef.py`.

To look at a page locally, serve the folder (`python3 -m http.server`) rather
than opening the file: `kit.js` and `tokens.js` load beside it. A page looked at that way
keeps picks in that browser only; send me the published Artifact, whose
picks the database keeps (a preview window that opens on his screen is not
the published page).

## Rules for mocks

- Draw in units and with tokens only, the same ones the C code uses; a mock
  that invents a size shows something the handheld cannot have.
- Show both themes when the decision touches color.
- Mark today's option `today` and a recommendation `suggested`.
- The page's own chrome (`.zk-*`) is not part of the design system and stays
  quiet so it does not argue with the screens.
